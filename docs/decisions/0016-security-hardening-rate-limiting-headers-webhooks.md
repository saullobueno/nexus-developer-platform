# 0016 — Security hardening: rate limiting, security headers e webhooks com segredo hasheado

## Status
Aceita

## Contexto
A spec (seção 29) pede, além do que já existia (autenticação JWT, RBAC, object-level authorization em praticamente toda query desde a Phase 2, validação Zod em toda fronteira de API, audit logs com UI desde a Phase 16): rate limiting, cookies seguros, CSP/security headers, hashing de API keys/segredos e "nunca confiar em IDs vindos do frontend sem autorizar no backend" (já seguido consistentemente). Faltava concretamente: (1) nenhum rate limiting em nenhuma rota, deixando `/auth/login` aberto a brute-force; (2) nenhum security header (helmet ou manual); (3) a tabela `webhooks` (com coluna `secret_hash`) existe desde a Phase 1 e nunca foi usada — era o único pedaço do schema de segurança sem nenhuma feature por trás.

## Decisão
- **Rate limiting**: `@nestjs/throttler` (v6.5.0, verificada via `npm view`) como `APP_GUARD` global — 120 requisições/60s por IP em qualquer rota, e um limite mais restrito de 10/60s especificamente em `POST /auth/login` via `@Throttle({ default: { ttl: 60_000, limit: 10 } })`, para mitigar brute-force sem quebrar o uso legítimo do resto da API. `apps/api/test/auth.e2e-spec.ts` ganhou um teste que dispara logins até observar `429`.
- **Security headers**: `helmet` (v8.3.0) em `main.ts`, com `contentSecurityPolicy: false` — a API não serve HTML/assets (isso é `apps/web`, em outra origem), então CSP aqui não protege nada real e quebraria clients simples (supertest, `fetch` do frontend); os demais headers do helmet (HSTS, `X-Content-Type-Options`, `X-Frame-Options` etc.) continuam ativos.
- **Cookies**: revisados e já estavam corretos desde a Phase 2 (`httpOnly: true`, `secure: NODE_ENV === "production"`, `sameSite: "lax"`) — nenhuma mudança necessária, só confirmação.
- **Webhooks**: `WebhooksModule` novo (`apps/api/src/webhooks/`) usa a tabela `webhooks` já existente. `POST /webhooks` gera um segredo aleatório (`crypto.randomBytes(24)`), retorna-o em texto puro **apenas na resposta de criação**, e persiste só o hash via `hashPassword` (bcrypt, o mesmo helper de `@nexus/auth` usado para senhas — nenhuma dependência nova). `GET /webhooks` nunca expõe `secretHash` nem o segredo. `DELETE /webhooks/:id` é escopado por `organizationId` (testado contra vazamento cross-org). Tudo auditado via `AuditService`, mascarando o segredo no `after` do log.

## Alternativas consideradas
- **CSP restritiva na API**: rejeitada — a API não renderiza HTML, então CSP não tem superfície para proteger; o lugar certo para isso é o `next.config` de `apps/web`, fora do escopo desta fase.
- **Disparo real de entrega dos webhooks (outbound HTTP para a `url` cadastrada quando eventos do `RealtimeEventBusService` ocorrem)**: considerado e descartado por ora. A coluna `secret_hash` (hash unidirecional, bcrypt) é o formato certo para *verificar* um segredo apresentado depois — não para assinar entregas repetidas (HMAC exige o segredo em texto puro a cada envio, que deliberadamente não persistimos). Construir a assinatura corretamente exigiria mudar o formato de armazenamento do segredo (ex.: criptografia reversível), o que não foi pedido por nenhum caso de uso concreto ainda. Documentar isso aqui em vez de forçar uma entrega "que funciona mas assina errado" evita o tipo de meio-implementação que o projeto evita (ver ADR 0015).
- **Limite de login mais agressivo (ex. 5/min)**: descartado numericamente — o teste de rate limiting precisa disparar `429` de forma determinística sem exigir uma janela de tempo maior que a suíte inteira; 10/min ainda é uma mitigação real contra brute-force (a maioria dos ataques de força bruta precisa de milhares de tentativas) e é compatível com os testes e2e existentes que já fazem múltiplos logins na mesma suíte.

## Consequências
- Webhooks hoje são só CRUD com segredo hasheado — não disparam nada sozinhos. Se uma fase futura quiser notificações outbound reais, o caminho natural é reaproveitar `RealtimeEventBusService` (Phase 14) e decidir explicitamente como o segredo será armazenado para permitir assinatura (provavelmente não mais `secret_hash`, e sim um segredo criptografado reversivelmente).
- Gaps de segurança que continuam documentados e não implementados, por não terem infraestrutura real por trás (mesma lógica da ADR 0015): 2FA, SSO/OAuth, criptografia em repouso para `integrations.config` (gap já registrado na ADR 0012), e verificação de auth no servidor durante SSR do `apps/web` (hoje client-side via `AuthGuard`, ver nota em `CLAUDE.md`).
