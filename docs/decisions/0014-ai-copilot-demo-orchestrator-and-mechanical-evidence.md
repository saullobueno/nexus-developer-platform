# 0014 — AI Copilot: orchestrator demo determinístico e evidência montada mecanicamente

## Status
Aceita

## Contexto
A spec da Phase 15 (seções 19-20) pede um AI Engineering Copilot com Vercel AI SDK + Anthropic/OpenAI, tool calling sobre 12 ferramentas somente-leitura + 4 mutáveis, resposta estruturada `{summary, findings, evidence, confidence, suggestedActions, requiresApproval}`, "nunca inventar evidências", aprovação humana obrigatória para ações mutáveis, e auditoria completa (`ai_agent_runs`/`ai_messages`/`ai_tool_calls`/`ai_usage`, já no schema desde a Phase 1). O ambiente onde este projeto foi construído não tem `ANTHROPIC_API_KEY`/`OPENAI_API_KEY` nem acesso de rede garantido para chamar esses provedores — e a spec (seção 27, Demo Mode) exige que tudo funcione sem credenciais externas.

Além disso, o pacote `ai` (Vercel AI SDK) está na major v7 — uma mudança grande em relação a versões anteriores mais conhecidas: `generateObject`/`streamObject` continuam existindo, mas a API de `generateText`/`tool()`/`stopWhen` mudou substancialmente (`maxSteps` virou `stopWhen: stepCountIs(n)`, por exemplo). A verificação foi feita baixando os pacotes (`ai@7.0.97`, `@ai-sdk/anthropic@4.0.52`) via `npm pack` e inspecionando `dist/index.d.ts` diretamente, já que a documentação viva não estava disponível — mesma disciplina usada nas fases anteriores diante de version drift (ex. TanStack Table na Phase 5).

## Decisão
- **Duas implementações do orchestrator, escolhidas pela mesma lógica de `resolveAdapter` da Phase 13**: `runRealOrchestrator` (Vercel AI SDK real, `generateText` + `tool()` + `stopWhen: stepCountIs(5)`, contra Anthropic ou OpenAI conforme a env var presente) e `runDemoOrchestrator` (determinístico, por palavra-chave, sem nenhuma chamada de rede). `runCopilotQuery` cai para o demo sempre que `DEMO_MODE=true` ou nenhuma API key está configurada — nunca falha por falta de credencial.
- **`findings`/`evidence` são montados mecanicamente a partir do resultado real das ferramentas, nunca pedidos ao modelo como JSON livre.** `evidence` é literalmente `{tool, input, output}` de cada chamada de ferramenta executada; `findings` é derivado do formato do output (contagem de itens, chaves presentes). Isso evita depender da funcionalidade de "structured output" do SDK v7 (que mudou de forma incerta) e, mais importante, é a garantia mais forte contra alucinação: a evidência É o dado real, não uma descrição gerada por LLM do dado real.
- **`confidence` é heurístico, não pedido ao modelo**: 0 quando nenhuma ferramenta pôde ser selecionada (pergunta não reconhecida), 0.3 quando a ferramenta certa foi chamada mas não retornou dados, 0.75/0.7 quando há dados. Isso é honesto sobre os limites do sistema em vez de inventar uma métrica de confiança sofisticada não verificável.
- **`suggestedActions` nunca são executadas automaticamente.** No modo demo, uma regra simples (serviço com deploy mais recente `successful` + pergunta menciona degradação) propõe `rollback_deployment`. No modo real, uma segunda chamada `generateText` (não `generateObject`, por segurança) pede um array JSON de ações recomendadas com um catálogo textual das 4 ferramentas mutáveis — o `JSON.parse` é envolto em try/catch que retorna `[]` em qualquer falha, nunca propagando um erro de parsing para o usuário.
- **Aprovação humana é aplicada na camada de aplicação, não no mecanismo `needsApproval`/`toolApproval` do SDK.** Cada `suggestedAction` vira uma linha em `ai_tool_calls` com `isMutating=true, approvedAt=null, output=null` assim que o run termina. A execução real só acontece em `POST /ai-copilot/tool-calls/:id/approve`, que chama diretamente o método de serviço já existente (`DeploymentsService.rollback`, `IncidentsService.create` etc.) e grava `approvedAt`+`output`+audit log. Essa camada é 100% testável e não depende de uma feature experimental do SDK v7 que não pôde ser exercitada neste ambiente.
- Os `*Service` de outros módulos (Services, Deployments, Observability, Incidents, Docs, Teams, Pipelines, FeatureFlags) são reaproveitados como providers diretos em `AiCopilotModule` (não via `imports`, que não os exportam) — todas as suas dependências (`DATABASE_CLIENT`, `AuditService`, `RealtimeEventBusService`) são globais, então isso é seguro e não duplica rotas.
- `ai.run.started`/`ai.run.completed` (spec seção 28) passaram a ser emitidos pelo Realtime — o item que a ADR 0013 deixou pendente por falta de uma feature real que os disparasse.
- Novas permissions `ai_copilot:read` (todas as roles) e `ai_copilot:use` (todas exceto viewer — perguntar e aprovar ações são capacidades operacionais, não deveriam ficar disponíveis a um papel somente-leitura).

## Alternativas consideradas
- **`generateObject`/`output` estruturado do SDK para toda a resposta**: rejeitado — a API de structured output do `ai` v7 (`Output`/`output` parameter em `generateText`) não pôde ser verificada com confiança suficiente sem documentação viva, e usar `generateObject` para tudo arriscaria o modelo "inventar" `findings`/`evidence` em vez de refletir exatamente o que as ferramentas retornaram. Preferimos determinismo mecânico onde a spec exige "nunca inventar evidências".
- **`needsApproval`/`toolApproval` nativos do SDK**: rejeitado por agora — são recursos "experimental_" na v7 com uma superfície de API grande e não verificável neste ambiente (sem chave real para exercitar o fluxo completo); a aprovação em nível de aplicação é mais simples, testável e não amarra a UX de aprovação a uma feature específica do SDK que pode mudar.
- **`trigger_deployment` como criação de deployment do zero**: rejeitado — não existe um endpoint real de "criar deployment novo" no domínio hoje (só retry/rollback de um deployment existente); mapear para `DeploymentsService.retry` é a capacidade real mais próxima, documentada aqui em vez de inventada silenciosamente.

## Consequências
- O caminho `runRealOrchestrator` não é exercitado por nenhum teste automatizado deste projeto (não há credencial nem rede disponível) — typechecked e revisado manualmente contra os `.d.ts` reais do SDK, mas sem cobertura de execução. Se um operador configurar `ANTHROPIC_API_KEY`/`OPENAI_API_KEY` em produção, validar esse caminho manualmente é um passo necessário antes de confiar nele.
- Se a Phase 20-equivalente (AI Audit & Evaluation, já parcialmente coberta por `ai_agent_runs`/`GET /ai-copilot/runs`) precisar de um dataset de avaliação automatizado, o `runDemoOrchestrator` já cobre as 5 perguntas de exemplo da spec (seção 19) e parte do dataset de avaliação (seção 20) — perguntas fora do catálogo de ferramentas (ex. "Which services violate SLO?") retornam confiança 0 honestamente, o que já é o comportamento desejável para avaliação de "hallucination".
